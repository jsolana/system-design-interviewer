# Idempotency

## Definition
A repeated operation has the same effect as running it once.

## Why it matters
Webhooks and retries deliver the same event multiple times.

## How it works
Stripe's webhook triggers the transaction (ticket -> sold, booking -> confirmed); the handler uses bookingId and checks the current state before applying, because Stripe retries.

## Variants and techniques
Payments: Stripe.js tokenizes the card (the server never sees the number, PCI) and a PaymentIntent is created.

## Trade-offs
Requires deduplication state/key.

## When to use it / when not to
Always in webhook consumers, at-least-once queues and payments.

## Additional detail
- [[ad-click-aggregator]]: HMAC-signed impression ID + Redis cache to discard duplicate clicks; writing to the stream before the cache avoids losing clicks.

## Additional detail (Xu Vol. 1, ch. 10)
In notifications, exactly-once delivery is not achievable in a distributed system; duplication is reduced with **dedupe by event ID**: when an event arrives, check whether it has already been seen and, if so, discard it. See [[notification-system]].

## Additional detail (DDIA, chs. 4, 9 and 12)
- **End-to-end argument**: reliability at the level of TCP, the DB or the stream processor does not prevent duplicates when the client retries after a timeout; the solution is a **unique operation/request ID** generated on the client (UUID or hash of form fields) propagated all the way to the DB and checked with a uniqueness constraint. See [[exactly-once-processing]].
- Retrying an aborted transaction is not safe if the network error hid the fact that it was committed ([[transactions-and-isolation-levels]]).
- In RPC/REST, requests must be idempotent or handled with IDs ([[encoding-and-schema-evolution]]).

## Additional detail (Xu & Lam Vol. 2, chs. 7 and 11)
- **Payments**: exactly-once = at-least-once (retry with backoff) + at-most-once (idempotency). `idempotency-key` (UUID generated by the client, expires; in e-commerce it can be the cart ID) and a DB unique constraint: insert first; if the key already exists, return the state of the previous request; concurrent requests with the same key -> 429. With the PSP, a unique nonce/token per payment order. See [[payment-system]].
- **Reservations**: a `reservation_id` generated by the server when creating the order and used as the PK prevents double booking from a double click ([[hotel-reservation]]).

## Additional detail (Brandur idempotency keys; Pragmatic Engineer payments)
- Brandur (https://brandur.org/idempotency-keys): client sends a unique key; server stores key + request params + `locked_at` + a **recovery point** + eventually the response. A retry resumes from the last recovery point or returns the stored result. Keep keys ~24h (reaper deletes after ~72h): near-term correctness, not a permanent record.
- **Atomic phases**: group local writes into DB transactions between *foreign state mutations* (calls that cannot be rolled back: a Stripe charge, an email, even publishing to Kafka). Key upsert is its own phase, each foreign call its own phase. Example recovery points: started, ride_created, charge_created, finished; run under SERIALIZABLE with a lock timeout.
- Failure handling: concurrent conflict -> 409, other errors -> 500 and unlock; permanent failure (card decline) stores the error response; transient failures tell the client to retry; the downstream's own idempotency key protects against a crash mid-call; a *completer* process finishes abandoned requests; follow-up jobs staged transactionally ([[transactional-outbox]]).
- Trade-offs: far more complex than one DB transaction per request (prefer that when possible); non-idempotent foreign APIs force treating ambiguous failures as failed; non-ACID stores make every write a foreign mutation; goal: "passively safe" backends that reach a stable state after any failure.
- Pragmatic Engineer (payments, Uber): idempotency via versioning + optimistic locking on a strongly consistent store, because the messaging layer is at-least-once (Kafka, lossless cluster; exactly-once judged too complex). Strong consistency for critical state (payment initiated), eventual for recent-transaction lists.
- Note: a senior answer states where the idempotency key is checked, what is stored with it, and how retries resume after partial failure.
