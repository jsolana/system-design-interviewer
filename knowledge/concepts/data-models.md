# Data models

## Definition
Data models determine how the problem is thought about and which queries are natural: relational (tables and joins), document (hierarchical JSON) and graph (vertices and edges).

## Why it matters
Choosing the right model simplifies code and queries; a wrong choice leads to manual joins or rigid schemas.

## How it works
- **Relacional**: tables, joins, normalization, strong support for many-to-one/many-to-many joins.
- **Documento** (MongoDB, CouchDB): self-contained JSON documents; better **locality** (the whole profile in one read) and less *impedance mismatch*; natural one-to-many (tree). Weak at many-to-many and joins (done in the application). References by ID. The whole document is updated (small changes rewrite everything).
- **Schema-on-write** (relacional) vs **schema-on-read** (document: "schemaless" = implicit, useful with heterogeneous data).
- **Normalization vs denormalization**: store IDs (a name changes in one place) vs duplicate (fast reads, costlier writes); Twitter timeline example.
- **Grafos**: property graph (Neo4j, cypher), triple-store (RDF, SPARQL), Datalog. For highly connected many-to-many relationships and variable-length (recursive) queries, which are hard in SQL.
- Lenguajes: **declarative** (SQL, CSS) lets the optimizer parallelize and change the plan, vs imperative; MapReduce as a mix.

## Variants and techniques
- Converging models: PostgreSQL/MySQL with JSON, document databases with joins.
- **Analytical models**: star schema (fact table + dimensions), snowflake ([[olap-columnar-stores]]).
- Event/derived views ([[event-sourcing]]).

## Trade-offs
| Model | Strong | Weak |
|---|---|---|
| Relational | joins, many-to-many, integrity | impedance mismatch, rigid schema |
| Document | locality, flexibility | joins, partial writes |
| Graph | arbitrary relationships | general use |

## When to use it / when not to
Tree-shaped data read as a whole -> document; highly interrelated data -> relational or graph. Combining systems is common (polyglot persistence).

## Additional detail (DDIA 2nd edition, ch. 3)
*Verification note:* the 1st-edition entry matches the 2nd edition (now ch. 3 "Data Models and Query Languages"); differences and additions:
- **Schema-on-read vs schema-on-write** is likened to dynamic vs static typing; schema-on-read fits heterogeneous data or structures controlled by external systems. Migrations: adding a column with default NULL is fast and the backfill can be done at read time; `UPDATE` of a whole large table is slow.
- **Locality**: document stored as one contiguous string (BSON, etc.); advantage only if you need most of it, and the whole document is rewritten on update. Locality also exists in relational/wide-column systems: Spanner interleaved tables, Oracle multi-table index clusters, Bigtable/HBase column families. Document "one-to-few" vs huge lists (comments on a celebrity post) which should be separate rows.
- **Normalization with hydration**: normalized = fast writes/slow reads, denormalized = the opposite; denormalization is derived data. Twitter-style timelines store IDs only and hydrate them at read time ([[materialized-views]]). Joins are not an inherent scalability blocker.
- **ORM** criticisms: N+1 query problem, schema generated by ORM awkward for analytics, mostly OLTP-only.
- **Analytics schemas**: star, snowflake, dimensional modeling and **one big table (OBT)**; fact tables often >100 columns; one row per event/product bought; date as dimension (holidays).
- Convergence: relational DBs with JSON types and indexes inside documents; document DBs with joins ($lookup), secondary indexes, declarative queries (MongoDB aggregation pipeline).
- **Graphs**: adjacency list (traversals) vs adjacency matrix (ML); property graph (Neo4j, Memgraph, KuzuDB, Neptune; Cypher/openCypher, Apache AGE), triple stores (Datomic, SPARQL), Datalog, recursive CTEs in SQL (WITH RECURSIVE) for variable-length paths, Gremlin.
- **New: GraphQL**: client-specified response shape; intentionally limited (no recursion, no arbitrary filters) because queries come from untrusted clients; can sit on any database; duplicates data in responses by design.
- **New: Event sourcing and CQRS** now live in this chapter (see [[event-sourcing]]): events in past tense, materialized views/projections, commands vs facts.
- **New: DataFrames, matrices, arrays**: Pandas/R/Spark/Dask DataFrames manipulated imperatively; relational table -> sparse matrix (pivot) and one-hot encoding for ML; array databases (TileDB) for scientific rasters; also used for financial time series.
- Historical context: network/hierarchical models lost to relational; NoSQL and NewSQL were buzzwords whose lasting effect is the document model.
